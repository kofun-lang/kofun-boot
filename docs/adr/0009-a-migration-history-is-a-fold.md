# 9. A migration history is a fold, so drift needs no database

Date: 2026-10-04

## Status

Accepted.

## Context

To learn what schema a migration history produces, Prisma's `migrate dev`
replays the history into a shadow database: a second database server, created
and dropped to compute one value. Atlas does the same with a dev database, and
pins the migration directory with a checksum file (`atlas.sum`) so that an
edited migration is detected. drizzle-kit diffs against snapshot JSON kept
beside each migration instead of against a database, which trusts that the
snapshots still describe the SQL beside them.

All three keep the migration's meaning in SQL text. So computing what a history
produces needs something that executes SQL, or a second artifact that is
trusted to agree with it.

## Decision

A migration is a value, and applying it is a pure function:

```
apply : Schema -> Migration -> SchemaStep    # the schema after, and what happened
```

So a history is a fold over `apply`, starting from the empty schema. The
shadow database is `replay(history)`, a function call that runs at build time
on both backends. Drift is `drift(declared, replay(history))`, which returns
`InSync(live)` or `Diverged(key)`.

SQL is a projection of the same values. `contracts/schema.sql` and
`contracts/migrations.sql` are generated from what the binary printed,
committed so a reviewer reads the SQL that will run, and regenerated by the
gate, which fails on any difference.

A step that `apply` refuses is not folded around. A history with a refused
step describes no database, and the replay reports the step and its outcome.

## Consequences

- No database is needed to detect drift, to plan the next migration, or to
  ask what the schema was at any earlier step: `replay(n)` is the database
  after step `n`.
- Whether the SQL means the same thing as the values is checked once, against
  a real PostgreSQL. `tests/schema/postgres.sh` builds one database from the
  migration SQL and one from the declared DDL and requires identical
  schema-only dumps. It also requires a negative control, the declared DDL
  with one `NOT NULL` removed, to differ.
- Data migrations, meaning updates to rows rather than to the schema, are not
  covered. They will be `Cmd` values in the history, interpreted by the shell
  inside the migration's transaction ([#53](https://github.com/kofun-lang/kofun-boot/issues/53)). Until then the backfill
  policy records a precondition, and the SQL projection prints it as a comment
  instead of inventing a value.
- Released history is append-only by convention and review, not yet by gate.
  The release gate will pin the history prefix at each tag ([#52](https://github.com/kofun-lang/kofun-boot/issues/52)).
